## 1.5 확정 수치

하루 기준선이다. 이 표의 값 하나를 고치면 **r 이 움직인다**(4.3).

| 항목 | 값 | 자리 |
|---|---|---|
| 고기 세트 | 2시간마다 **30개** | `IdleRewardManager.MeatPerSet` |
| 고기 하루 유입 | **360** | 30 x 12세트 |
| 고기 최대 저장 | **60세트 = 1,800** (소탕 360회분, 5일치) | `MaxMeatSetCount` |
| 소탕 1회 비용 | 고기 **5** | `SweepRules.StaminaCostPerSweep` |
| **하루 소탕** | **72회** | 360 / 5 |
| 방치 자동전투 | 시간당 1회, 24시간 상한 = **24회/일** | `IdleRewardManager` |
| **하루 총 클리어** | **96회** | 방치 24 + 소탕 72 |
| 클리어당 티켓 | **1장** | `StageRewardCalculator.PinballTicketPerClear` |
| **하루 핀볼** | **96발** | 96 클리어 x 1장 / 발당 1장 |
| 핀볼 칸 고기 | **[1, 1, 25, 1, 1]** | `PinballRewardDatabase.asset` |
| 발당 고기 기댓값 | **1.24** | 칸 확률 [.2475 .2475 **.01** .2475 .2475] 가중 |
| **회수율 r** | **0.331** | 119 / 360 |
| **경제 승수** | **x1.49** | 1 / (1 - r) |

**소탕이 공급의 3/4 을 차지하는 것이 핵심이다.** 예전에는 방치가 72회(무료)·소탕이 24회여서
공급의 1/4 에만 고기가 붙었고, 그래서 고기가 게이트 구실을 못 하고 r 도 전체에 작용하지 못했다.
총 클리어 96회는 그대로 두고 **구성만 뒤집었다**.

## 1.51 성장 페이스

**레벨 상한이 없다.** `TryLevelUp` 은 `SetLevel(current + 1)` 만 하고 상한을 보지 않는다 —
재화만 있으면 무한히 올라간다. 그래서 "만렙까지"가 아니라 구간별 소요 일수로 적는다.

| 축 | 도달 |
|---|---|
| 다이스 마일스톤 3 / 6 / 9 / 12 | **0.3 / 1.9 / 5.0 / 9.5일** |
| 장비 보석 슬롯 1 / 10 / 20 / 30 / 40 | **즉시 / 1.2 / 4.3 / 9.3 / 16.2일** |
| 레어 다이스 lv12 | 5종 **21일** · 1종 집중 4.2일 |
| 킹 다이스 lv12 | 5종 **41일** · 1종 집중 8.2일 |
| 유물 소환 10 / 50 / 100회 | **2.5 / 38 / 138일** |
| **전체 lv12 (골드 기준)** | **21.9일** ← 병목 |

**티어 순서가 선다.** 기본 9.5일 < 레어 21일 < 킹 41일.

**원소 스크롤은 종류별로 따로 들어와 5종이 병렬로 오른다.** 종류 간 교환이 없어서 한 다이스에
몰아줄 수 없다 — 다섯이 항상 같은 레벨이다. 반면 레어석·신화석은 **공유 재화**라 한 종에
몰면 5배 빠르고, 거기서만 빌드 선택이 생긴다.

### 다이스 스크롤은 공급을 줄여서 맞췄다

예전에는 종당 하루 1,252장이 들어왔다. 마일스톤(3·6·9·12)까지 필요한 것이 1,188장이라
**첫날에 넷이 다 지나갔다** — 12레벨까지를 어렵게 만들려던 설계가 통째로 무의미해지는 자리였다.

**비용을 올리는 쪽으로는 못 고친다.** 강화 비용이 선형이라 초반을 늘리면 후반이 같은 배수로
늘어난다 — lv12 를 열흘로 만들자고 비용을 올리면 lv100 이 78일에서 580일이 된다.
공급 축소만 초반에 선택적으로 듣는다.

### Gold 가 게이트다 (7.1 을 뒤집는다)

예전에는 하루 44,256 으로 강화 수요의 24배였다. 골드가 아무 제약이 아니었고 상점 골드
구매(8.7)를 쓸 이유도 없었다.

2,028 로 내린 것은 **골드를 병목으로 만들기 위해서**다.

```
전체 lv12 까지
  스크롤 기준   9.5일   (종류별 병렬이라 다 같이 오른다)
  골드   기준  21.9일   <- 2.3배 느리다
```

**스크롤은 종류별로 따로 들어오는데 골드는 하나를 나눠 쓴다.** 그래서 골드가 모자라면 유저가
"이번엔 뭘 올릴까"를 매번 고르게 된다 — 스크롤만으로는 그 선택이 안 생긴다. 하루 2,028 이면
lv12 부근에서 약 3레벨이고, 성장 트랙이 11개(다이스 5 + 장비 6)라 매일 셋을 고르는 셈이다.

7.1 은 Scroll 을 게이트로 잡았지만 **지금은 Gold 가 게이트다.** 7.1 의 "Gold 는 핀볼로
우회되니 게이트 부적격"은 핀볼 골드도 같이 줄여서 해소했다(발당 6.96).

## 1.55 Pinball_Base 보상

**Base 는 티어 1~3 만 준다.** 상위 재화(티어 4~6)는 Pinball_Bonus 한 곳에서만 나와야
성장 페이스가 한 손잡이에 모인다(3.2 · 5.1).

| 칸 | 확률 | 보상 |
|---|---|---|
| 0 · 1 · 3 · 4 | 각 24.75% | Gold 3~5 + 고기 1 |
| **2 (잭팟)** | **1%** | **Gold 300 + 고기 25** |

| 핀 | 조건 | 보상 |
|---|---|---|
| 스크롤핀 (tag 1) | 10히트 | **다이스 스크롤 10** — 5종 중 랜덤 1종 |
| 장비핀 (tag 2) | 15히트 | **장비 스크롤 10** — 6종 중 랜덤 1종 |
| 센터핀 (tag 3) | 25히트 | 없음 — 보너스 라운드를 여는 트리거 |

### 잭팟은 금액이 아니라 확률이 만든다

다섯 칸이 고른 확률(0.16~0.22)이면 **고기 잭팟을 만들 수가 없다.** 발당 최소 1개씩만 줘도
96발이면 96개인데 회수율 상한(r = 0.35, 하루 126개)이 거의 차서 남는 몫이 30개뿐이고,
그것을 다시 나누면 한 번에 몇 개가 안 된다.

한 칸을 1% 로 깎으면 그 칸에 25개를 넣어도 기댓값이 0.25 밖에 안 오른다.

```
고기 기댓값 = 0.99 x 1 + 0.01 x 25 = 1.24
              x 96발 = 119개  ->  r = 0.331   (상한 0.35)

잭팟 25개 = 소탕 5회분, 하루 약 1회
```

**tag 1·2 가 바뀐 자리다.** 예전에는 무료젬 10(티어 6)과 레어석 1(티어 4)이라 Base 가
상위 재화를 흘리고 있었다. 레어석의 당시 근거였던 "핀볼에 다이스 성장 축이 비어 있다"는
보너스 라운드의 레어석 핀·신화석 핀이 채웠다.

스크롤로 바꾼 것은 세 가지가 맞아서다 — **티어가 맞고**(Base 티어 3 ↔ 스크롤 티어 3),
**r 을 안 건드리고**(고기가 아니다), **Bonus 의 페이스를 안 흔든다**.

**다만 양이 게이트를 넘으면 안 된다.** 핀이 많이 주면 Scroll 이 핀볼로 우회된다.
두 핀 모두 소탕 공급의 **10% 안팎**으로 잡았다.

| 핀 | 하루 완성(추정) | 종당 공급 | 소탕 종당 | 비중 |
|---|---|---|---|---|
| 스크롤핀 | 5회 | 10 | 115 | 9% |
| 장비핀 | 3회 | 5 | 48 | 11% |

완성 빈도는 센터핀(25히트가 하루 2회)에서 역산한 추정이다. **실측하면 양부터 다시 잡는다.**

**랜덤 1종은 `pickOneAtRandom` 이 한다.** 풀을 코드에 박지 않고 에셋에 종류를 나열해 두면
무엇이 나올 수 있는지가 그대로 보인다. 임계치를 여러 번 넘으면 넘은 횟수만큼 따로 뽑는다 —
한 번 뽑아 배수로 주면 고배율일수록 종류가 덜 갈려서 5.2 의 압축 불변식이 깨진다.

그 자리이고, **실측하면 여기부터 고친다** — 고치면 위 일일 페이스가 통째로 따라 움직인다.

## 3. 두 개의 축

### 3.1 flow 와 stock

공급처는 성격이 둘로 갈린다. 이 구분을 놓치면 "핀볼이 다 준다"가 문제로 보이지만, 실제로는 문제가 아니다.

| 축 | 공급처 | 리듬 | 성격 |
|---|---|---|---|
| **flow (반복)** | MeetRoasting, IdleReward, StageClear/Sweep, Pinball_Base, Pinball_Bonus | 매일 | **시간** → 재화 |
| **stock (1회성)** | StageReward, StarReward, Tower | 진도 | **스펙** → 재화 |

Tower는 flow가 아니다. 각 층 **최초 클리어에만** 보상이 나오고 반복 플레이가 없다
(2026-09-05 확정, `TowerRunManager.BuildClearRewards` 주석). 그래서 Tower는 핀볼과 경쟁하지 않는다.
Tower의 고유 역할은 **킹 다이스 라인**이다 — 탑이 킹을 열고, 킹을 올릴 재료도 탑이 준다.

### 3.2 그래서 상위 재화의 반복 수급처는 Pinball_Bonus 하나뿐이다

티어 4~6 재화(FreeGem, RareStone, MythicStone, RelicTicket)의 나머지 수급처는 전부 stock이다.
**이것은 의도된 설계다.** "유저는 소탕과 핀볼만 하면 된다"는 방향의 필연적 결과이고,
부수 효과로 **상위 경제의 밸런싱 손잡이가 한 곳에 모인다**.

다만 대가가 있다 — 유일한 수도꼭지가 확률 콘텐츠라, 여기 분산이 크면 운 나쁜 유저는
상위 성장이 며칠씩 멈춘다. 대안 수급처가 없다. 그래서 5.1의 저분산 요구가 취향이 아니라 **구조적 필수**다.

대박(스파이크)은 stock 3종이 담당한다. 두 축이 역할을 나눈다.

### 3.3 RelicTicket 대표를 Tower로 옮기지 않는 이유

유물은 **소환형 지속 소모** 시스템이다(`UIRelicSummonDialog`, `RelicManager`의 `cost.ticketCost`).
지속 소모에는 지속 공급이 필요하고, 1회성인 Tower는 대표 수급처가 될 수 없다.
Tower는 서브로 둔다.

## 4. 고기 루프 (핵심)

### 4.1 구조

```
고기 ──Sweep──> 티켓 ──Pinball_Base──> 고기
                  └──Pinball_Bonus──> 상위 재화 전부
```

닫힌 고리이며, **의도적으로 닫았다.**

**회수율 r = 0.3.** 절대 1에 근접시키지 않는다.

```
r = (Sweep 1회당 티켓) x (티켓당 핀볼 시행) x (핀볼 1회당 고기 기댓값)
                       / (Sweep 1회당 고기 소모)
```

r < 1이면 등비급수로 수렴한다. **총 스태미나 = 고기 공급 x 1/(1-r).**

| r | 승수 |
|---|---|
| 0.3 | x1.43 |
| 0.5 | x2.0 |
| 0.7 | x3.3 |
| 0.9 | x10 |

### 4.2 왜 넣는가 — 그리고 왜 일일 상한이 없는가

**넣는 이유는 세션 길이가 아니다.** 고기 총량을 1.43배로 올려도 세션은 똑같이 길어진다.
루프만이 주는 것은 따로 있다 — **핀볼이 "보상을 받는 곳"에서 "소탕을 더 하는 연료"로 바뀐다.**
유저 머릿속에 `핀볼 → 소탕 → 스펙`이 한 줄로 선다. 두 콘텐츠가 인과로 묶이는 것이 값어치이고,
총량 증가로는 만들 수 없다.

스테이지에 막힌 유저의 행동이 이렇게 달라진다.

| | 유저 행동 |
|---|---|
| 핀볼 없음 | 소탕 → 재도전 → 끝 |
| 핀볼 있음 | 소탕 → 핀볼 → 고기 없음 → 잠수 |
| **핀볼이 고기도 지급** | 소탕 → 핀볼 → 소탕 → 핀볼 → … → 재도전 |

**일일 상한을 두지 않는다.** 이유는 둘이다.

1. **중복 장치다.** r < 1 자체가 이미 수학적 상한이다. 오래 플레이한 유저는 같은 웅덩이를
   더 빨리 퍼낼 뿐 x1.43을 넘지 못한다. 상한이 추가로 잠그는 인플레는 없다.
2. **상한은 판타지를 죽인다.** 도박 콘텐츠의 동력은 기댓값이 아니라 *상방이 닫혀 있지 않다는 느낌*이다.
   "운 좋으면 계속 돌 수 있겠는데?"가 핀볼을 한 판 더 돌리게 만든다. 상한을 본 순간 핀볼은 숙제가 된다.

상한이 실제로 제공했을 이점은 "막힌 유저에게만 기울이기" 하나였고, 판타지와 맞바꿨다.

### 4.3 r 은 파생값이다 — 반드시 테스트로 고정한다

**r은 어디에도 적혀 있지 않다.** 네 개 수치의 곱이고, 넷은 서로 다른 시점에 서로 다른 이유로 만져진다.
티켓을 후하게 준 날, 핀볼 고기를 조금 올린 날, 소탕 비용을 낮춘 날 —
아무도 r을 건드린 적이 없는데 r이 움직인다. 그리고 1/(1-r)은 위로 갈수록 급격하다.
0.3 → 0.6은 "두 배 버프"로 보이지만 승수는 1.43 → 2.5다.

일일 상한을 뺐으므로 **r이 유일한 방어선이다. 2차 방어선이 없다.**

**장치는 걸려 있다.** `SweepEconomy`(static)가 r을 계산하고 `SweepEconomyTests`가 잠근다.

| 테스트 | 막는 것 |
|---|---|
| `회수율이_상한을_넘지_않는다` | `r > 0.35` → 실패 |
| `회수율이_목표_0_3_근처다` | 위아래 0.05 — 낮아도 인과가 안 읽힌다 |
| `발산하지_않는다` | 승수가 2를 넘으면 실패 |
| `발당_고기는_칸_확률의_가중평균이다` | 바닥값 0 금지 (5.1) |

r은 네 수치의 곱이라 **넷 중 무엇을 고쳐도 이 테스트가 반응한다.** 터졌다면 "테스트가 낡았다"가
아니라 경제 승수가 바뀌었다는 뜻이다.

- 기댓값에 **잭팟을 포함**해서 계산한다. 잭팟을 "연출용"으로 보고 키우면 r이 조용히 오른다.
- 루프는 코드를 읽어서는 보이지 않는다(네 파일에 흩어져 있다). 터질 때는
  "왜 재화가 이렇게 많지?"로만 나타난다.
- 핀볼 칸 보상은 SO가 정본인데 헤드리스에서 SO가 안 뜬다. 그래서 `SweepEconomy`에
  **선언값**을 두고 테스트가 그것을 두드린다 — 에셋을 고치면 선언값도 같이 고칠 것.

## 5. 핀볼 분산 정책

### 5.1 주머니가 둘이므로 성격도 둘이다

| | 열리는 조건 | 지급 | 분산 | 역할 |
|---|---|---|---|---|
| **Pinball_Base** | 공을 쏘면 계속 | 고기, 골드 | **높게** | 도박 판타지 |
| **Pinball_Bonus** | 센터핀 게이지 충전 | 상위 재화 4종 | **낮게** | 성장 페이스 |

상위 재화는 Bonus에서만 나오므로, Base가 아무리 요동쳐도 성장 속도는 흔들리지 않는다.
한 콘텐츠 안에서 도박 맛과 안정 공급이 공존한다.

**고기 지급 형태 — "평소 조금 + 가끔 왕창".**

```
밋밋:   5 4 6 5 5 4 6 5 …     → 3판 만에 "30% 환급이네" 학습. 기대가 안 생긴다
뾰족:   2 2 2 2 2 30 2 2 2 …  → 평균은 같은데 저 30이 다음 판을 돌리게 한다
```

두 가지를 지킨다.

1. **바닥값을 0으로 두지 않는다.** 잭팟이 안 터져도 조금씩 쌓여야 한다.
   잭팟은 덤이고, 기본 회수는 평소값이 담당한다.
2. **조절은 기댓값으로 한다.** 잭팟이 커도 확률이 낮으면 기댓값은 낮다.
   r이 넘으면 잭팟 확률이나 크기를 내리지, 규칙에 예외를 만들지 않는다(5.2).

`BonusDiceDatabase` 주석의 "조금만 참여해도 좋은 것을 거의 다 가져간다",
"빈손으로 나가면 이 컨텐츠는 존재 이유를 잃는다"가 Bonus 쪽 저분산 요구와 같은 말이다.

### 5.2 배율 일관성 — 예외를 만들지 않는다

현재 코드는 모든 것이 발사 배율에 비례한다.

| 항목 | 위치 |
|---|---|
| 티켓 소모 | `PinballManager.ShotCost` → `PinballRules.ScaleAmount` |
| 착지 보상 | `PinballManager.GetLandingRewards` |
| 특수핀 게이지 | `PinballManager.ResolveSpecialHit` |

**그래서 1배로 N번 = N배로 1번이다. 배율은 스킵이 아니라 압축이다.**
이 등가가 깨지면 유저는 저배율로 오래 돌리는 것이 이득이 되고, 핀볼은 노동이 된다.
배율 언락 조건이 보유 티켓 수이므로(`IsMultiplierUnlocked`), 티켓을 후하게 줄수록 고배율이 저절로 열린다.
**티켓은 마음껏 뿌려도 된다.**

**잭팟도 예외 없이 배율을 탄다.** 잭팟만 빼면 10배 발사는 티켓을 10배 쓰고 잭팟은 1배로 받아
고배율이 손해가 된다. 유저는 이걸 알아채고, "어떤 건 배수로 주고 어떤 건 안 주네"는
도박 콘텐츠가 가장 빨리 신뢰를 잃는 방식이다.

배수가 위험한 것이 아니라 **티켓을 안 먹고 곱해지는 것**이 위험하다.

| 배수 | 티켓 소모 | r 영향 | 판정 |
|---|---|---|---|
| 발사 배율 | 비례해서 먹음 | 없음 | 곱한다 |
| 잭팟 x 발사 배율 | 비례해서 먹음 | 없음 | 곱한다 |
| 콤보 · 연쇄 보너스 | 안 먹음 | 상승 | 기댓값에 포함해 계산 |
| 잭팟 → 게이지 → 보너스 재진입 → 잭팟 | 안 먹음 | **발산 가능** | **막는다** |

마지막 줄이 유일하게 실제로 발산할 수 있는 구조다. 막는 방법은 배율 예외가 아니라
**한 세션 내 보너스 진입 횟수 상한**이다. 유저에게 "한 판에 보너스는 최대 N번"으로 깔끔하게 읽히고
배율 일관성을 건드리지 않는다.

## 6. 젬 계열

### 6.1 FreeGem 은 유지하고, 교환비는 1:1

문서와 코드가 3중으로 갈려 있었다. **1:1로 확정한다.**

| 출처 | 값 |
|---|---|
| `BMDesign.md` 2.3 | 1 유료젬 → 10 무료젬 |
| `ShopPackageDesign.md` 8.5-3 | 미정 |
| `ShopDatabase.PopulateDefaults` | 1 : 1 |

단순 임시값 문제가 아니다. **1:10이면 FreeGem은 별개 재화가 아니라 잔돈이다**(PaidGem = 10원, FreeGem = 1원).
같은 재화의 두 단위라면 "따로 있을 필요가 없어 보인다"는 직관이 구조적으로 옳다.
1:1이면 상점 가격을 FreeGem 하나로 통일하고 유료젬은 원화로만 표기하면 된다.

**FreeGem 을 없애지 않는 이유.**

1. **환불 · 회계.** 유료재화는 환불 의무가 있고 미사용분은 이연수익이다. 무료 지급분과 섞이면
   "환불 요청분이 산 것인가 받은 것인가"를 가리려고 소모 순서 정책을 강제로 만들어야 한다.
   코드 문제가 아니라 운영 리스크다.
2. **가격 앵커.** `ShopPackageDesign.md` 8.1-3이 "유저가 10원 = 1젬으로 즉시 환산할 수 있어야 한다"를
   설계 규칙으로 확정했다. PaidGem을 보상으로 뿌리면 앵커가 깨진다. 300젬을 주는 것은
   3,000원 할인 쿠폰을 뿌리는 것이다.
3. **뿌릴 자유.** `BMDesign.md` 2.3이 "무료젬은 넉넉하게 뿌리는 것을 기본 방향"으로 잡았다.
   PaidGem으로는 불가능하다.

**다만 FreeGem의 역할을 좁힌다.** 지금 FreeGem의 사용처는 전부 "다른 재화로의 변환"이라
소멸하지 않는다 — 진짜 sink가 없다. 상위 티어가 하위 티어를 전부 덮어쓰면
RareStone·MythicStone의 수급처를 따로 설계한 의미가 사라진다.

- FreeGem의 주 역할은 **뽑기 재화**다(6.2).
- 하위 재화 구매(8.6 다이스석 / 8.7 골드)는 남기되 **누진 또는 일일 한도**를 반드시 건다.
  8.7은 이미 누진을 확정했고, 8.6은 개발 편의로 한도를 뺀 상태다 — 재분배 때 되살린다.

### 6.2 Jewelry 는 상점 뽑기 전용

핀볼에서 레어리티별로 차등 지급하지 않는다.

1. **FreeGem의 유일한 진짜 sink다.** 보석은 합성 시스템이 있어(`UIMergePopup`) 양이 곧 스펙이고,
   랜덤이라 소비량이 무한히 열린다. 핀볼로 옮기면 FreeGem은 환전소만 남는다.
2. **유료 패키지 구성품이다.** `BMDesign.md` 2.4가 보석을 "성장 패키지 구성의 주요 축"으로 잡았고
   동시에 **단가가 미정**이라고 적었다. 지급량을 정할 기준 자체가 없는 상태에서 무료로 뿌리면
   패키지 가치가 먼저 깎인다.
3. 핀볼-보석 연결을 원하면 보석을 직접 주지 말고 **보너스 상위 족보에서 FreeGem을 크게** 준다.
   어차피 그 FreeGem이 뽑기로 흘러가므로 결과는 같고 재화 종류가 늘지 않는다.

### 6.3 일일상점은 삭제한다

핀볼이 들어오면서 역할이 사라졌다.

1. **중복이 기본값에 드러나 있다.** 일일상점 기본 구성이 NormalScroll 5 / Gold 100,000인데,
   정확히 StageClear와 Pinball_Base가 주는 것들이다.
2. **고유 가치가 이미 다른 섹션에 있다.** "확정으로 콕 집어 산다"는 8.6 다이스석 상점과
   8.7 골드 상점이 한다. 일일상점은 그것의 랜덤 슬롯 버전일 뿐이다.
3. **유지비가 크다.** 일일 리셋, 슬롯 랜덤 테이블, 갱신 2종(광고 2회 / 젬 3회), 할인 확률 슬롯 —
   시스템 4개를 굴려서 8.6/8.7과 같은 것을 얻는다.

| 잃는 것 | 대체 |
|---|---|
| 매일 접속 이유 | IdleReward + 출석이 담당 |
| **광고 시청 지점** (`dailyAdRefreshPerDay`) | **핀볼 티켓 광고 충전으로 이전** |

광고 대체는 빠뜨리면 안 된다. `BMDesign.md`의 광고제거권(3,000원)이 팔리려면
광고가 거슬릴 만큼 노출되어야 하는데, 일일상점을 빼면 그 지점이 사라진다.
핀볼이 일일 루프의 중심이므로 티켓 충전이 자연스러운 자리다.

## 7. 유저 행동 설계 — 교차 플레이

목표는 **교차**다.

```
목표:  소탕 → 핀볼 → 재도전 → 소탕 → 핀볼 → 재도전 …
아님:  소탕 → 핀볼 → 소탕 → 핀볼 → 소탕 → 핀볼 → 재도전
```

**루프는 교차를 만들지 않는다.** 표에서 Stamina 사용처가 Stage와 Sweep 둘 다이므로
재도전과 소탕이 같은 지갑을 쓴다. 그러면 유저는 합리적으로 **고기를 최대로 불린 다음 쓴다** —
재도전은 실패 가능성이 있고 고기를 태우므로 맨 뒤로 밀린다. 루프를 넣을수록 몰아치기가 강해진다.

교차를 만드는 것은 **강화 임계점**이다. `소탕 → 재료 → 강화 → "이제 될 것 같은데?" → 재도전`.
이 충동이 사이클을 끊는다.

### 7.1 게이트는 Gold 다 (원래는 Scroll 이었다)

강화는 Gold와 Scroll을 둘 다 먹고, 임계점은 **부족한 쪽**이 결정한다.
둘 다 빡빡하면 유저는 무엇을 모아야 할지 모르고, "몇 번 더 돌면 강화된다"가 읽히지 않는다.

**처음에는 Scroll 을 게이트로 잡았다.** Gold 는 핀볼에서도 나와 소탕 횟수와 직결되지 않으니
부적격이라고 봤다.

**그 판단을 1.51 이 뒤집었다.** 이유는 둘이다.

1. **Scroll 로는 선택이 안 생긴다.** 원소 스크롤은 종류별로 따로 들어와 5종이 병렬로 오른다.
   종류 간 교환도 없어서 다섯 다이스가 항상 같은 레벨이다 — 유저가 고를 것이 없다.
2. **Gold 는 하나를 나눠 쓴다.** 그래서 골드를 조이면 "이번엔 뭘 올릴까"가 매번 생긴다.
   성장 트랙이 11개(다이스 5 + 장비 6)인데 하루에 3레벨치만 들어오면 매일 셋을 고르는 셈이다.

Gold 의 결격 사유였던 "핀볼로 우회된다"는 **핀볼 골드도 같이 줄여서** 해소했다(발당 6.96).

| 재화 | 하루 공급 | 전체 lv12 소요 | 게이트 |
|---|---|---|---|
| **Gold** | 2,028 (공유) | **21.9일** | **여기** |
| 원소스크롤 | 125 (종당) | 9.5일 | 남는다 |
| 장비스크롤 | 53 (종당) | 1.7일 | 남는다 |

### 7.2 수치 목표

- **하루 3레벨.** 골드 2,028 을 lv12 부근 강화비(약 670)로 나눈 값이다.
  트랙이 11개이므로 매일 셋을 고르게 된다 — 이 비율이 곧 "선택의 빡빡함"이다.
- DiceScroll과 EquipScroll은 수급처가 같으므로(StageClear + IdleReward) 소탕 한 번에 둘 다 쌓인다.
  **둘 중 먼저 차는 쪽**이 임계점이 되어 빈도가 두 배가 된다. 이 구조는 그대로 둔다.
- **체감 폭이 필요하다.** 스펙 1% 오르는 강화로는 재도전 충동이 안 생긴다.
  강화 한 단계가 레벨업처럼 딱 떨어져야 하고, 강화 직후에 "지금 도전 가능해 보이는 스테이지"를
  UI로 밀어주는 것이 좋다. 충동을 만들었으면 바로 받아준다.

## 8. 재분배 작업 순서

손잡이는 셋이고, 가운데 것만 직접 만질 수 없다.

| 손잡이 | 역할 | 성격 |
|---|---|---|
| 고기 회복 속도 (MeetRoasting / IdleReward) | 입구 — 하루 총량 | 직접 수치 |
| **루프 회수율 r** | 증폭 — x1/(1-r) | **파생값** |
| 보너스 라운드 지급량 | 출구 — 한 판의 가치 | 직접 수치 |

나머지 재화는 전부 이 셋 사이의 환율이다. 순서는 아래를 따른다.

1. **고기 회복 속도**를 정한다 — 하루에 소탕 몇 회인가.
2. **소탕 1회 산출**을 정한다 — Scroll(게이트), Gold(여유), PinballTicket.
3. 1과 2에서 **r을 계산**하고 0.3에 맞도록 핀볼 고기 기댓값을 역산한다. 테스트를 건다(4.3).
4. **보너스 라운드 지급량**을 정한다 — 상위 재화 4종의 일일 페이스가 여기서 결정된다.
5. stock 3종(StageReward / StarReward / Tower)을 **스파이크**로 배치한다. flow와 겹치지 않게.

## 9. 되돌리기 쉬운 항목 (주의)

아래 셋은 근거를 모르면 "개선"처럼 보이는 방향으로 되돌아가기 쉽다. 손대기 전에 해당 절을 읽는다.

| 항목 | 되돌아가는 모습 | 결과 |
|---|---|---|
| **r 테스트** (4.3) | "이 이상한 테스트 뭐지?" → 삭제 | 유일한 방어선이 사라지고 루프가 조용히 새기 시작한다 |
| **Pinball_Base 고기 지급** (4) | "핀볼에서 고기 주면 무한 파밍 아닌가?" → 제거 | 리텐션 장치를 잃는다. r < 1이면 발산하지 않는다 |
| **배율 일관성** (5.2) | "잭팟은 너무 커지니까 배수에서 빼자" | 고배율이 손해가 되어 핀볼이 노동이 된다. 유저는 알아챈다 |

### 10.0 탑을 건드리지 않은 이유

`TowerFormula.BandRewardDia`(10 + 2×구간)와 `BandRewardMaterial`(12 + 3×구간)은 그대로 두었다.
구간 하나가 flow 하루치에 못 미쳐 스파이크로는 약하지만, 올리지 않았다.

1. **누적으로 보면 이미 크다.** 60구간을 다 오르면 FreeGem 4,140 · MythicStone 6,030 으로,
   신화석 기준 하루치의 75일분이다. 탑은 이미 신화석의 주 공급원이다.
2. **탑 진행 속도를 모른다.** 구간별 값은 "한 구간 오르는 데 며칠"을 알아야 정해진다.
   그 데이터 없이 재화 분배만 보고 배수를 곱하면 숫자가 맞는 척만 한다.
3. **다른 기획서와 테스트가 물고 있다.** `InfiniteTowerDesign.md` 의 곡선이고
   `TowerFormulaTests` 가 값을 잠그고 있다. 탑 설계를 같이 보지 않고 바꾸면 두 문서가 어긋난다.

탑 진행 속도가 잡히면 그때 1.7의 스파이크 기준(하루치 1배)으로 다시 계산한다.
